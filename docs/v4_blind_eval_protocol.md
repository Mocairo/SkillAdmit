# V4 Blind-Style Admission Evaluation Protocol

Last updated: 2026-05-21

## 1. Purpose

V4 is designed to test whether the current SkillAdmit controller generalizes
beyond the development/regression sets used during earlier tuning.

The goal is not to reach 100% on v4. The goal is to obtain an honest first-pass
measurement after freezing the controller.

## 2. Frozen Controller

The controller snapshot for this evaluation is:

```text
skilladmit/controllers/rule_based_controller_v3_frozen.py
```

This file was copied from the current rule-based controller before generating
and evaluating v4.

Do not edit this frozen file when analyzing v4 errors. If a future method is
improved from v4 errors, create a new controller file and treat v4 as a
development set.

## 3. V4 Sample File

V4 samples are generated by:

```text
scripts/build_v4_blind_admission_samples.py
```

This file does the following:

```text
creates 50 curated admission samples
keeps the five labels balanced
uses 10 examples per label
writes JSONL to benchmark/admission_samples/v4_blind_admission_samples.jsonl
```

Labels:

```text
discard: 10
store_as_memory: 10
distill_into_skill: 10
promote_to_rule: 10
defer: 10
```

The v4 samples introduce domains beyond the original Python import/debug set:

```text
CLI argument parsing
JSON schema compatibility
encoding and CSV loading
package data loading
pytest fixture scope
rate limits and API pagination
datetime/timezone handling
subprocess launch context
state migration and data deletion risks
runtime configuration and environment memory
experience-management rules
provider-specific uncertainty
```

## 4. Evaluation Command

Run:

```bash
python scripts/build_v4_blind_admission_samples.py
python scripts/evaluate_frozen_controller.py
```

The frozen evaluation script:

```text
scripts/evaluate_frozen_controller.py
```

uses:

```text
skilladmit.controllers.rule_based_controller_v3_frozen.RuleBasedSkillAdmitController
```

and writes predictions to:

```text
benchmark/admission_samples/v4_frozen_controller_predictions.jsonl
```

## 5. Error Inspection

Run:

```bash
python scripts/inspect_frozen_controller_errors.py
```

This reads the frozen prediction file instead of re-running the current
controller. That matters because the current controller may change in later
experiments.

## 7. Main Failure Modes

The frozen controller is strongest on:

```text
distill_into_skill
promote_to_rule
```

The frozen controller is weakest on:

```text
discard
store_as_memory
```

Major observed failures:

```text
harmful candidates without known marker phrases are often deferred
project-specific memory is often deferred unless it matches existing memory markers
some procedural skills are over-promoted to rule when their candidate_rule is broad
some genuinely deferred setup conventions are over-admitted as distill_into_skill
```

This is a good result scientifically because it exposes where the rule-based
baseline does not generalize.

## 8. How To Use V4 Going Forward

There are two valid paths.

Path A: keep v4 as a real evaluation set.

```text
Do not tune any method on v4 errors.
Report 54.0% as the frozen controller's v4 result.
Create a separate development set for future controller improvement.
```

Path B: use v4 for error analysis and improvement.

```text
Rename v4 conceptually as a development set.
Do not report it as held-out.
Create a new v5 blind set after improvements.
Evaluate v5 once with the improved frozen method.
```

For paper credibility, Path A is cleaner. For engineering progress, Path B is
faster. Do not mix the two.

## 9. Recommended Next Step

The next method-improvement target should be a new controller version, not an
edit to the frozen controller.

Suggested file:

```text
skilladmit/controllers/rule_based_controller_v4_dev.py
```

Suggested evaluation flow:

```bash
python scripts/inspect_frozen_controller_errors.py
# implement v4_dev controller separately
# evaluate v4_dev on v1/v2/v3/v4 as development evidence
# then create v5_blind_admission_samples.jsonl
# freeze v4_dev before evaluating v5
```

The most important improvements to test:

```text
better harmful-workaround detection beyond exact phrases
stronger project-specific memory detection
clearer distinction between procedural skill and global rule
explicit uncertainty detection for convention/setup conflicts
```
