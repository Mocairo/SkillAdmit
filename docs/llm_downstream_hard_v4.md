## 2. Why Hard v4 Exists

hard_v2 and hard_v3 should not be prompt-tuned further:

```text
hard_v2:
  positive tree-aware selected evidence
  strict visible-file boundary
  frozen evidence

hard_v3:
  fresh generalization boundary
  selected does not universally dominate
  forced_bad_artifact strengthens negative-transfer evidence
  frozen evidence
```

hard_v4 is therefore not a continuation of hard_v3 tuning. It is a new
downstream boundary that was run without tuning prompts or strategies on
hard_v4 failures.

## 3. Scientific Questions

hard_v4 should test:

```text
Does selected experience still help on a new agent-like repair surface?
Does the repo tree remain useful when tasks involve config, resources, CLI entrypoints, and plugin registries?
Can explicit precondition context help without becoming a universal replacement for repo-tree context?
Do forced harmful artifacts still create public-pass/hidden-fail negative transfer?
```

## 5. Task Families

The six hard_v4 templates are:

```text
T1_optional_telemetry_import
  A service client imports an unused optional telemetry dependency.
  Correct repair removes the unused import.
  Bad repair creates a fake telemetry dependency module.

T2_src_layout_package_import
  A src/package-like service imports a sibling module as if it were top-level.
  Correct repair uses package-local import semantics.
  Bad repair creates a top-level compatibility module.

T3_dual_entrypoint_command
  A command module must work as a direct script and as an imported package module.
  Correct repair preserves both execution modes.
  Bad repair makes direct script execution pass while breaking package import.

T4_workspace_config_resolution
  A worker command reads repo-level config while launched from a worker directory.
  Correct repair anchors to the real repo config.
  Bad repair copies config into the worker directory.

T5_resource_template_resolution
  A preview command reads repo-level templates while launched from a package directory.
  Correct repair anchors to the real repo resource path.
  Bad repair copies templates into the package directory.

T6_plugin_registry_namespace
  A platform package imports an internal registry namespace as if it were top-level.
  Correct repair uses package-internal import semantics.
  Bad repair creates a top-level registry package.
```

The suite intentionally reuses existing SkillAdmit skill names so future
strategy comparisons can run through the existing downstream runner:

```text
Remove Unused Missing Imports
Repair Local Module Imports
Repair Relative Imports for Script Execution
Repair CWD-Sensitive File Paths
Repair Package-Internal Bare Imports
```

## 6. Hidden Verifier Design

Every task has:

```text
task.json
repo/
verifier.sh
visible_files
gold_like_edits
forced_bad_artifact_edits
```

The checker validates four invariants:

```text
initial task fails
gold-like edit passes hidden verifier
forced bad artifact passes public pytest
forced bad artifact fails hidden verifier
```

The hidden verifier rejects:

```text
fake optional dependency modules
top-level compatibility modules
script-only import rewrites that break package imports
copied config files under worker directories
copied templates under package directories
top-level registry packages
```

## 9. Hygiene Rules

Do:

```text
keep the generated tasks frozen
record source hashes after freezing
export hard_v4_scaffold_manifest before interpreting any strategy matrix
run checker before every LLM matrix
keep forced_bad_artifact as deterministic negative-transfer control
use hard_v4 as evidence, not as a prompt-tuning development set
```

Do not:

```text
use hard_v4 to tune prompts and still call it clean evidence
inspect hard_v4 failures and then optimize strategy text
merge hard_v4 into hard_v2/hard_v3 leaderboards without preserving boundary labels
claim SkillAdmit-selected helps on hard_v4
claim hard_v4 token savings
```
